# Supabase — the periplus backend

One schema for every tracking link: LoRa, Bluetooth Channel Sounding, and
cellular. It never collides with the pre-existing `public.tags` table.


> ⚠️ Do **not** modify or drop the existing non-MVP `public.tags` table.

## Objects

| Object | Type | Purpose |
| --- | --- | --- |
| `public.devices` | table | Every tag and every gateway. `kind` = what it is, `link` = how it talks. Devices that write also hold an `ingest_key_hash`. |
| `public.readings` | table | Append-only history of every observation, whatever produced it. |
| `public.latest_positions` | view | Newest reading per device, joined to the device and to whoever reported it. What the clients read. |
| `public.ingest(text, jsonb)` | function | `security definer` RPC — the only write path. |
| `public.register_device(...)` | function | Issues an ingest key. Returns it once; `service_role` only. |

### Why one table set and not one per radio

The backend used to be `lora_gateways` + `lora_tags` + `lora_tag_readings` for
LoRa and `cs_tags` + `cs_observations` for Channel Sounding, with an ingest
function each. Adding cellular trackers would have meant a third set, a third
RPC and a third pair of views.

What the three have in common is the entire model: **a device reports an
observation about itself or about another device.** The radio is an attribute
(`devices.link`), not a schema.

What is deliberately *not* collapsed:

* `lat`/`lng` and `distance_m` stay separate columns. A Channel Sounding
  reading measures a distance from the gateway, not a point — folding it into a
  coordinate would store a guess where a measurement belongs.
* The circle a ranged tag is somewhere on (`origin_lat`, `origin_lng`,
  `radius_m`) is computed in `latest_positions` and never stored.

## Apply the migrations

### SQL editor / psql (the supported path)

Paste each file in `migrations/` into the Supabase SQL editor in timestamp
order and run it. All are idempotent.

On a **fresh** database, `20260908120000_unify_device_schema.sql` alone is
enough — its backfill blocks are guarded on tables that will not exist. On a
database carrying earlier bring-up data, run the lot in order: that migration
copies the old rows across (ingest keys included, so gateways in the field keep
working) before dropping the old tables.

### Why not `supabase db push`?

`supabase link` works, and `supabase migration list` correctly shows the
migrations as applied. **`db push` does not work on this project**, by nature
rather than by mistake:

This project is shared with a second, unrelated GPS application whose
migrations live in a different repository. `db push` requires every remote
migration to have a local file, so it aborts with
`LegacyDbPushMissingLocalError` and suggests either marking the remote
migrations `reverted` or running `db pull`.

**Do not follow either suggestion.** `--status reverted` would falsify the
history of migrations that really are applied — including the other
application's. `db pull` would import that application's entire schema
(`tags`, `zones`, `machines`, `profiles`, …) into this repo.

Use the SQL editor instead.

## Register devices / validate

`seed.sql` registers a gateway and runs one validation reading:

```bash
psql "$DATABASE_URL" -f supabase/seed.sql
```

Then verify:

```sql
select device_id, kind, link, status, lat, lng, distance_m, recorded_at
from public.latest_positions
order by recorded_at desc;
```

One query covers every link — a LoRa tag, a ranged tag and a cellular tracker
all come back from the same view.

## Security notes (MVP only)

* An ingest key is MVP-level shared-secret auth, **not** production auth. Only
  its SHA-256 hash is stored (`devices.ingest_key_hash`), matching the
  convention used by `public.tags.device_secret_hash`.
* RLS allows **read** for `anon`/`authenticated`; **writes** only happen through
  the `security definer` `ingest` function, which validates the key.
* `ingest_key_hash` is excluded by a **column grant** — `select *` on `devices`
  is denied for anon, so a client must list columns. Any new column on `devices`
  needs its own `grant select (col)`.
* Keys are generated by `register_device`, printed once, and never committed.
  Rotate by re-running it with the same `device_id`:
  ```sql
  select public.register_device('GW001', 'gateway', 'lora');
  ```
* `latest_positions` is declared `security_invoker = on` so it enforces the
  querying role's RLS rather than the view creator's.
* `EXECUTE` on `ingest` is granted to `anon` (devices and the bridge) and
  `service_role` only — not to `authenticated`. `register_device` is
  `service_role` only: a role that could mint keys would make the key pointless.
